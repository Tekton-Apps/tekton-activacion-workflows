# Pestañas separadas de la entidad, parámetros validados, request_id e historial leído desde n8n

Se suma la pestaña **RH** (liquidaciones) junto a la de contabilidad (Workflow INC / SAC). Eso rompe tres supuestos de v1 —"una pestaña = una entidad", "el trigger no lleva datos" y "este panel no muestra historial"— y obliga a decidir cómo se reemplazan:

- **Pestaña ≠ entidad.** Tekton sigue siendo la única entidad (la organización dueña del panel), pero adentro hay áreas con públicos distintos: RH no debe ver ni correr los P&L, y contabilidad no debe generar liquidaciones. El registro pasa a ser de pestañas (`lib/tabs.ts`: `{ id, label, allowedEmailsEnv }`, el `content` se arma en `page.tsx`), cada una con su whitelist propia (`TEKTON_ALLOWED_EMAILS` para contabilidad, `TEKTON_RH_ALLOWED_EMAILS` para RH). Cada workflow apunta a su pestaña y hereda de ahí la whitelist, en vez de repetir el nombre de env var. `page.tsx` filtra qué pestañas se renderizan y **cada route de servidor revalida la whitelist de la pestaña correspondiente en cada request** — nunca "pertenece a alguna whitelist". El login sigue exigiendo pertenecer al menos a una.
- **Parámetros validados en el servidor, con lista blanca.** La liquidación necesita datos (DNI, fecha de cese, motivo, montos). `/api/rh/liquidacion` acepta solo los campos conocidos, con tipo y rango (`lib/liquidacion.ts`, compartido con el cliente para habilitar el botón), rechaza cualquier campo extra y arma el payload a n8n desde cero — nunca reenvía el body del cliente. Las reglas de negocio (si el DNI existe, si el usuario puede liquidar) siguen en n8n, que responde 422 con `errores[]`; el panel los muestra tal cual.
- **request_id generado en el servidor.** Cada disparo (RH y las cards de contabilidad) lleva un `request_id` (`crypto.randomUUID()`) y el `solicitante_email` de la sesión, ambos puestos por la API route — el cliente no puede elegirlos ni falsificarlos. Es la clave para cruzar un disparo del panel con su fila en el historial de n8n y con los logs de Vercel.
- **Historial leído desde n8n, sin DB.** n8n ya registra cada ejecución en su Data Table de ejecuciones; el panel la consulta vía `GET /api/executions?area=` → webhook de `N8N_TEKTON_EJECUCIONES_URL`. Se mantiene "sin base de datos" (CLAUDE.md): no hay RLS que mantener ni datos duplicados. El servidor solo deja pedir el área de una pestaña que el usuario tiene, y descarta links que no sean `https://` antes de devolverlos (los datos vienen de n8n pero se renderizan en el navegador).

## Consequences

- Sumar un área nueva = una entrada en `lib/tabs.ts` + su env var de whitelist + su contenido en `page.tsx`. Sumar un workflow de contabilidad sigue siendo una entrada en `lib/workflows.ts`.
- El CSP con `'unsafe-inline'` (ADR-0002) se revisó: ahora hay inputs de usuario (motivo) y datos de n8n renderizados en la página, pero todo pasa por el escape de React (sin `dangerouslySetInnerHTML`) y los links se filtran a `https://`. No se cambia todavía; si en el futuro se renderiza HTML de n8n, ahí sí corresponde el nonce.
- El historial depende de que n8n esté arriba: si el webhook falla, el panel muestra el error y no tiene copia propia. Es aceptable mientras sea una herramienta interna de pocos usuarios.
- Los workflows de n8n deben persistir el `request_id` que reciben; si lo ignoran, el historial igual funciona pero se pierde el cruce con los logs del panel.
